1. System overview

What the project is, what changes dynamically, and what it intentionally does not try to be.

The application models a social network as an undirected dynamic graph G = (V, E). Each person is a vertex/node. Each accepted friendship is an undirected edge. Profile metadata such as age group, hometown, occupation, bio, and interests belongs to the node. Adding/removing users or friendships changes the graph topology; editing profile data changes metadata and may change recommendation scores without directly changing topology.

Vertices (V)

People with names and profile metadata.

Edges (E)

Accepted friendships. Friendship direction does not matter.

Candidate edges

Dashed suggestion lines computed from similarity but not yet real friendships.

Core capabilities

  • Create, edit, inspect, and remove profiles.
  • Add/remove friendships through controls, suggestion cards, or long-press graph gestures.
  • Visualize the live graph and inspect profile information by hover.
  • Run shortest-path, mutual-friend, strong-group, density, degree-centrality, and recommendation analysis.
  • Search for a person, focus a neighborhood, manually rearrange the graph, and preserve visual context during selection.
  • Persist recent data-changing activity in SQLite and show it in the Activity drawer.
Academic scope: this is a dynamic-graphs and social-network-analysis application, not a production social-media platform. Authentication, posts, private messaging, media uploads, and external social APIs are outside the current scope.

Example: adding a friendship

  1. The UI sends POST /api/friendships with two user IDs.
  2. Flask validates both users, prevents self-friendship, sorts IDs, and inserts the edge.
  3. The activity wrapper records the successful connection.
  4. The browser refreshes graph data and summary metrics.
  5. All future paths, mutual-friend results, degree values, strong groups, density, and suggestions can change because E changed.

Runtime entrypoint

Production starts activity_entry:app. That module imports the Flask application from app.py, installs persistent activity logging, and exposes the same Flask app to Gunicorn. The Docker/Procfile startup also runs the seed migration before starting Gunicorn.

4. SQLite data model

The persistent structures behind nodes, edges, interests, migration state, and history.

Referential integrity

Every SQLite connection enables PRAGMA foreign_keys = ON. Deleting a user cascades to friendship and user-interest records. This prevents orphaned edges and interest mappings.

Profile migration

The database initialization code checks existing users columns using PRAGMA table_info(users). If age group, hometown, occupation, or bio is missing from an older database, it adds that column with ALTER TABLE. This lets older deployments migrate forward without discarding data.

Interest normalization

Interests are trimmed, de-duplicated case-insensitively, limited to 40 characters each, and capped at 12 per profile. The user stores references to interest rows rather than repeating interest strings in every profile.

7. Graph algorithms

The analyses that operate on the current dynamic graph.

Shortest connection

nx.shortest_path() is run on an unweighted undirected graph. In this context it has BFS-style shortest-hop behavior: each friendship costs one hop. The client highlights every node and edge in the returned path and reports len(path)-1 degrees of separation.

Mutual friends

nx.common_neighbors(g, a, b) finds people directly connected to both selected users. The result is sorted by name and highlighted as nodes.

Most connected user

Degree is the number of real friendship edges touching a node. The summary calculates all degrees and returns every user tied for maximum degree. This is degree centrality in its raw degree-count form.

Density

density = 2|E| / (|V|(|V| - 1))

For an undirected simple graph, density describes the fraction of all possible friendship edges that currently exist. Dashed recommendation edges are never included.

Raw connected components

The backend can calculate ordinary connected components: if any path exists between two people, they belong to the same component. This raw definition is useful for reachability, but it is intentionally not the final UI definition of a social group.

8. Friend recommendation model

How profile similarity and graph topology become proposed edges.
Score = 60×Jaccard Interests + 20×Mutual-Friend Signal + 10×Same Hometown + 10×Same Age Group

Interest similarity

J(A,B) = |A ∩ B| / |A ∪ B|

Case-insensitive interest sets are compared with Jaccard similarity. If both users have no interests, this component is zero.

Mutual-friend signal

Common neighbors contribute up to 20 points. It is capped at three mutual friends: min(mutual_count, 3) / 3 × 20.

Candidate filtering

  • The selected user is excluded.
  • Existing friends are excluded.
  • Candidates with a final score of zero are excluded.
  • The backend returns the top six; the graph draws only the top three to limit clutter.

Graph representation

A recommendation is not a real edge. The graph draws it as a subtle dashed line and gives the suggested person a very light green treatment. Accepting the suggestion or long-pressing that person creates a real friendship row, removes the candidate status, and changes the topology.

9. Strong social groups and bridge handling

Why one cross-group friendship does not collapse two communities into one.

The final Groups UI uses a bridge-aware definition. A bridge is an edge whose removal increases the number of connected components. If two dense friendship communities are connected only through one such friendship, they remain separate strong groups for presentation purposes.

Group A: A — B — C — D | one bridge | Group B: E — F — G — H

For reachability, NetworkX still sees a path from Group A to Group B. For the Groups UI, the bridge is temporarily ignored and the remaining components are reported separately.

Algorithm used in graph_extras.js

  1. Create an adjacency map.
  2. Run depth-first search and assign discovery times.
  3. Maintain a low value for each node.
  4. An edge is a bridge when low(child) > discovery(parent).
  5. Traverse the graph again while skipping bridge edges.
  6. Sort resulting groups primarily by size.
Important distinction: /api/analysis/summary still returns raw connected components. After the summary loads, graph_extras.js recalculates bridge-aware communities in the browser and replaces the dashboard tile label/value with Strong groups. The Groups button is also replaced with the bridge-aware UI handler.

11. JavaScript architecture — file by file

The scripts deliberately load in order because later layers wrap and enhance earlier functions.
Load order: app.js → graph_extras.js → layout_lock.js → long_press_connect.js → interaction_enhancements.js → activity_log_ui.js. Later files depend on globals/functions defined earlier and sometimes replace a function with a wrapper that calls the previous implementation.

app.js — core application state and behavior

Defines shared globals including network, nodeSet, edgeSet, users, graphData, selectedNodeId, focusConnectedOnly, activeSuggestions, highlighted node/edge sets, hover/drag state, and a recommendation request token.

  • api() centralizes fetch, JSON parsing, and HTTP error conversion into JavaScript exceptions.
  • renderVisualState() is the central visual-state renderer: node colors, hidden state, real-edge emphasis, path highlights, and initial dashed suggestion edges.

graph_extras.js — strong communities and Find User

  • Implements bridge detection with DFS discovery/low-link values.
  • Overrides the visible Groups result and summary tile with bridge-aware Strong Groups.
  • Dynamically inserts the Find User input into the graph heading.
  • Name matching order is exact match → starts-with match → contains match.
  • Search acts like selecting the user: it sets selectedNodeId, updates profile/Person A, renders neighborhood emphasis, loads suggestion edges, then gently focuses the camera.
  • Zoom is restrained: very zoomed-out views increase scale modestly toward at most 0.65; otherwise only a slight increase up to 1.0.

layout_lock.js — stable selection, live drag physics

  • After initial stabilization, physics is disabled and positions are stored.
  • When visual state changes from a click/search/analysis, the current layout snapshot is captured and restored so selection itself does not rearrange the graph.
  • beginManualMove() turns physics on immediately while a node is being dragged, so connected nodes/lines react live.
  • endManualMove() leaves physics active for roughly 520 ms after release, then freezes the settled layout.
  • The camera position and scale are preserved through the manual-movement settle process.

long_press_connect.js — friend/unfriend gesture

  • A capture-phase pointerdown snapshots the already-selected person before vis-network can alter its own internal selection.
  • The vis hold event treats the held node as the target.
  • If source and target are not friends, POST creates the edge. If they are friends, DELETE removes it.
  • The source person remains selected after the mutation.
  • A possible click fired after a hold is suppressed so the target does not unintentionally become selected.
  • The code refreshes graph data without recreating the vis Network, preserving the current layout.

interaction_enhancements.js — graph interaction polish

  • Wraps renderVisualState() to give the top suggested nodes a very light green style.
  • Keeps suggested nodes and their dashed edges visible even when Focus mode hides unrelated people.
  • Replaces hover/drag handlers so profile tooltips disappear during dragging and remain suppressed briefly afterward.
  • Calls graphLayoutController.beginManualMove() on node drag start and endManualMove() on node drag end.

activity_log_ui.js — history interface

  • Dynamically adds the Activity button next to the live indicator.
  • Creates a Bootstrap offcanvas drawer.
  • Loads /api/activities?limit=60 when opened or manually refreshed.
  • Maps activity types to icons/labels and formats timestamps in the browser's local display format.

Why function wrapping is used

The project evolved feature-by-feature. Enhancement scripts preserve the core app.js behavior while layering specialized behavior. For example, layout_lock.js saves the current renderVisualState function, replaces it with a wrapper, calls the previous version, then restores coordinates. This avoids duplicating the entire core renderer, but means script order is important.

13. Graph visual language

What node/edge colors and line styles mean.
Normal userSelected userAlgorithm resultSuggested userReal friendship emphasisSuggested friendship
  • Normal blue node: ordinary person in the graph.
  • Selected blue node with stronger border: current neighborhood source.
  • Gray nodes: unrelated to the selected person's direct neighborhood.
  • Gold/orange: explicit analysis highlight, such as shortest-path or Find User highlight state when applicable.
  • Very pale green: a high-ranked suggested friend.
  • Solid edge: a real friendship stored in SQLite.
  • Dashed pale green edge: recommendation only; not counted as a friendship or in graph metrics.

Tooltip behavior

The tooltip is a custom HTML element rather than vis-network's native title tooltip. It uses canvas-to-DOM coordinate conversion so it follows the node while the graph is moving. Drag handlers explicitly hide/suppress it during manual node movement to prevent a popup from obscuring the drag.

14. Recent activity logging

How profile and graph mutations become persistent audit-style history.

activity_entry.py installs activity_log.install_activity_logging(app, DB_PATH) before Gunicorn serves requests. The installer creates the activity table and then wraps Flask mutation view functions already registered by app.py.

Events recorded

  • Profile created.
  • Profile removed.
  • Name, age group, hometown, occupation/role, or bio changes.
  • Interests added and interests removed, computed by comparing before/after snapshots.
  • Friendship created.
  • Friendship removed/unfriended.

Storage limits

  • Action type is capped at 40 characters.
  • Human-readable message is capped at 600 characters.
  • JSON metadata is capped at 2,000 characters.
  • Only the newest 300 rows are retained.
  • The API can return 1–100 rows per request; the UI requests 60.
The log begins only after the feature is installed. It cannot reconstruct mutations that occurred before activity logging existed.

15. Sample data and migration seeding

How the 50-person demonstration network is safely added without wiping user data.

seed_data.py defines SEED_VERSION = "50-profiles-v1", a 50-person fictional profile set, and 75 sample friendships arranged into recognizable communities. The seeder is additive: it inserts missing named sample users, enriches a matching sample user only when that existing profile has no profile details/interests, and uses INSERT OR IGNORE for sample friendships.

Version control

The app_meta table stores sample_dataset_version. If it already equals the current seed version, startup prints that the sample network is already seeded and stops without re-adding deleted sample users every restart.

Data themes

The profiles intentionally include overlapping interests and varied hometowns/age groups/occupations. This gives the recommendation model realistic non-zero candidates and makes group/path demonstrations meaningful. The data is fictional sample material for classroom/demo use.

16. Validation, data safety, and client escaping

Rules that prevent invalid graph/data states and unsafe rendering.
  • Name is required and capped at 80 characters.
  • Age group is capped at 30 characters; hometown/occupation at 80; bio at 240.
  • Interest strings are normalized, de-duplicated case-insensitively, capped to 40 characters and 12 entries.
  • User names and interest names have case-insensitive uniqueness behavior where appropriate.
  • Self-friendship is rejected.
  • Friendship IDs are sorted before storage, ensuring one canonical undirected pair.
  • Database uniqueness prevents duplicate friendship edges.
  • Foreign keys prevent invalid references and cascade deletes.
  • Frontend escapeHtml() is used when inserting user-provided names/details into HTML strings to reduce HTML injection risk.
  • The project deliberately avoids unnecessary sensitive fields such as exact birth date, contact details, gender, relationship status, or private messages.

18. Railway / production deployment

The exact production startup sequence and persistence requirement.

Docker startup

python seed_data.py → gunicorn activity_entry:app → bind 0.0.0.0:${PORT:-8080} → 2 workers, 2 threads, 60s timeout

The Procfile expresses the same essential flow for platforms that use it: run the seed migration, then serve activity_entry:app through Gunicorn on Railway's injected port.

Persistent SQLite

Railway volume mount: /data Environment variable: DB_PATH=/data/sna.db

Without a persistent volume, the container filesystem may be replaced on deployment and SQLite data can be lost. With DB_PATH=/data/sna.db and a mounted volume, profiles, friendships, interests, seed metadata, and activity history persist.

Why the server binds this way

Railway routes public traffic to the process listening on its assigned $PORT. Gunicorn therefore binds to 0.0.0.0, not localhost.

Why the current approach is appropriate for a classroom-sized dynamic network.

20. Current limitations and design choices

Important facts to state clearly instead of presenting the project as something it is not.
  • No authentication/authorization: anyone who can access the app can change the demo network.
  • SQLite: excellent for a small single-service academic project, but not designed for high-write multi-instance social-network production workloads.
  • Strong Groups is client-side: the dashboard/Groups UI uses bridge-aware groups while raw API summary/components still expose ordinary connected components.
  • JavaScript enhancement layering: later scripts wrap/replace earlier handlers. This keeps changes modular but makes script load order part of the architecture.
  • Activity history is mutation history, not full security audit logging: it does not identify authenticated actors because accounts do not exist.
  • Recommendation formula is interpretable and educational: it is not machine-learned and does not claim predictive accuracy.
  • Suggested edges are visual candidates only: they never affect NetworkX graph metrics until accepted.
  • Seed data is demonstration data: it should not be treated as empirical social-network data.

21. Suggested project-defense walkthrough

A concise order for demonstrating that the system is truly dynamic.
  1. Define the model: people = vertices; friendships = undirected edges; profile fields = node attributes.
  2. Show the live graph: point out real solid edges versus dashed suggested candidate edges.
  3. Select a user: explain direct-neighborhood emphasis, gray unrelated nodes, and top suggestions.
  4. Explain recommendations: 60% Jaccard interest similarity, 20% mutual-friend signal, 10% hometown, 10% age group.
  5. Create a dynamic edge: long-press a suggested/non-friend user or use Connect. Show how the dashed relation becomes a real edge.
  6. Run shortest path / mutual friends: show that analyses immediately reflect the changed topology.
  7. Show Strong Groups: explain why a single bridge does not merge otherwise separate communities.
  8. Move a node: demonstrate live physics during drag but stable layout during simple selection.
  9. Edit interests: show how metadata can change future candidate-edge ranking without directly changing E.
  10. Open Activity: show the recorded connection/profile/interest changes.
  11. Close with persistence/deployment: SQLite volume, Gunicorn, Railway, and versioned seed migration.
Key academic message: the system separates graph topology from vertex attributes. Topology drives paths, connectedness, degree, and density; metadata contributes to recommendation of possible future edges. Accepting a recommendation converts a metadata-informed candidate into a real topology change.

22. Glossary

Terms used throughout the application.
Vertex / Node

A person in the network.

Edge

A real accepted friendship between two people.

Candidate edge

A suggested friendship represented by a dashed line, not yet part of E.

Degree

Number of real friendship edges incident to a person.

Connected component

A maximal set in which every pair is connected by some path.

Bridge

An edge whose removal increases the number of connected components.

Strong group

This app's bridge-aware community: component after bridge-only ties are ignored.

Density

Existing real edges divided by all possible undirected edges.

Mutual friend

A node adjacent to both selected people.

Shortest path

Path containing the fewest friendship hops between two people.

Jaccard similarity

Intersection size divided by union size for two interest sets.

Topology

The actual node/edge structure, independent of profile metadata.
